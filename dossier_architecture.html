01 — Vue d'ensemble

Architecture logicielle

Le projet adopte la Clean Architecture d'Uncle Bob : les couches internes (domaine, use cases) ne dépendent jamais des couches externes (framework, base de données). La règle de dépendance va toujours vers l'intérieur.

💡 Clé de l'architecture : Le domaine ne contient aucun import Spring. Les repositories sont des interfaces dans le domaine (ports) et leurs implémentations vivent dans la couche adapter (adapters). La BeanConfiguration instancie les use cases manuellement, évitant que Spring pénètre dans le domaine.
02 — Principes

Principes SOLID

Chaque principe est illustré avec du code réel issu du projet.

S

Single Responsibility

Une classe = une seule raison de changer

Chaque use case gère une seule responsabilité. RedigerAvisImpl ne fait que créer un avis. ModererAvisImpl ne fait que modérer.

// ✅ Responsabilité unique : rédiger un avis
public class RedigerAvisImpl implements RedigerAvis {

    private final AvisRepository avisRepository;

    @Override
    public void executer(Avis avis) {
        // Uniquement : initialiser et sauvegarder
        avis.setStatut(StatutAvis.EN_ATTENTE);
        avis.setDateDenvoi(LocalDateTime.now());
        avisRepository.sauvegarder(avis);
    }
}

// ✅ Autre responsabilité : modérer un avis
public class ModererAvisImpl implements ModererAvis {
    public void validerAvis(Long id) { /* ... */ }
    public void rejeterAvis(Long id) { /* ... */ }
}
✓ Respecté
O

Open/Closed

Ouvert à l'extension, fermé à la modification

Les use cases sont des interfaces. Ajouter un nouveau comportement = créer une nouvelle implémentation sans toucher à l'existant.

// Interface fermée à la modification
public interface AjouterJeu {
    void executer(Jeu jeu);
}

// Implémentation actuelle
public class AjouterJeuImpl implements AjouterJeu {
    public void executer(Jeu jeu) {
        jeuRepository.sauvegarder(jeu);
    }
}

// Extension future possible : validation, notification
public class AjouterJeuAvecNotifImpl
    implements AjouterJeu {
    public void executer(Jeu jeu) {
        // + notifier les joueurs
    }
}
✓ Respecté
L

Liskov Substitution

Les sous-types sont substituables au type parent

Joueur étend Utilisateur et peut se substituer partout où un Utilisateur est attendu, sans altérer le comportement.

// Type parent : contrat général
public abstract class Utilisateur {
    private String pseudo;
    private String email;
    private String motDePasse;
    // getters / setters
}

// Joueur substitue Utilisateur sans briser le contrat
public class Joueur extends Utilisateur {
    private LocalDate dateDeNaissance;
    private List<Avis> avis;
    // Enrichit sans altérer le parent
}

// Utilisable partout où Utilisateur est attendu ✅
Utilisateur u = new Joueur();
✓ Respecté
I

Interface Segregation

Des interfaces spécifiques, pas une seule grosse

Chaque use case a sa propre interface. Les controllers n'injectent que ce dont ils ont besoin.

// ✅ Interfaces fines et ciblées
public interface AjouterJeu {
    void executer(Jeu jeu);
}
public interface ListerJeux {
    List<Jeu> executer();
}

// JeuController n'injecte que ce qu'il utilise
public class JeuController {
    private final AjouterJeu ajouterJeu;
    private final ListerJeux listerJeux;
    // Pas de dépendance sur ModererAvis !
}

// ❌ Ce qu'on aurait pu faire (à éviter)
// public interface JeuService {
//   void ajouter(); void lister(); void moderer()...
// }
✓ Respecté
D

Dependency Inversion

Les modules de haut niveau ne dépendent pas des modules de bas niveau — tous deux dépendent d'abstractions

Le domaine définit des interfaces (ports). Les adapters les implémentent. La BeanConfiguration injecte les implémentations sans que le domaine connaisse Spring.

// ✅ Le domaine définit l'abstraction (port)
public interface JeuRepository {           // dans domain/repository
    void sauvegarder(Jeu jeu);
    List<Jeu> recupererTous();
    Optional<Jeu> recupererParId(Long id);
}

// ✅ L'adapter (bas niveau) implémente l'interface
@Component
public class JeuPersistenceAdapter implements JeuRepository {  // dans adapter/persistence
    private final JeuJpaRepository jpaRepository;
    private final JeuPersistenceMapper mapper;
    // implémentation Spring/JPA totalement invisible du domaine
}

// ✅ La BeanConfiguration injecte sans Spring dans le domaine
@Configuration
public class BeanConfiguration {
    @Bean
    public AjouterJeu ajouterJeu(JeuRepository jeuRepository) {
        return new AjouterJeuImpl(jeuRepository);  // injection manuelle
    }
}

// ✅ AjouterJeuImpl ne connaît que l'interface, jamais Spring ni JPA
public class AjouterJeuImpl implements AjouterJeu {
    private final JeuRepository jeuRepository;  // abstraction, pas l'implémentation
    public void executer(Jeu jeu) {
        jeuRepository.sauvegarder(jeu);
    }
}
✓ Respecté — c'est le cœur de la Clean Architecture
03 — UML

Diagramme État-Transition — Objet Avis

Un avis suit un cycle de vie strict : il naît toujours en attente de modération, puis peut être validé ou rejeté. Un avis validé ne peut pas être rejeté directement (règle métier dans Avis.valider()).

new Avis() / setStatut(EN_ATTENTE)
⏳ EN_ATTENTE
validerAvis(id)
│ avis.valider() ▼
✅ VALIDE
│▼
rejeterAvis(id)
│ avis.rejeter() ▼
❌ REJETE
│▼ 
// Règle métier dans Avis.java (domaine)
public void valider() {
    // Un avis déjà validé/rejeté ne peut pas être re-validé
    if (this.statut == StatutAvis.EN_ATTENTE) {
        this.statut = StatutAvis.VALIDE;
    }
}

public void rejeter() {
    this.statut = StatutAvis.REJETE;
}

Diagramme de Séquence — Use Case « Ajouter un jeu »

Ce diagramme montre le flux complet depuis la requête HTTP jusqu'à la base de données, en traversant toutes les couches de la Clean Architecture.

// Flux complet dans JeuController.java
@PostMapping
public void creerJeu(@RequestBody JeuRequest request) {
    Jeu nouveauJeu = new Jeu();
    nouveauJeu.setNom(request.getNom());
    nouveauJeu.setDescription(request.getDescription());
    nouveauJeu.setPrix(request.getPrix());
    ajouterJeu.executer(nouveauJeu);  // → AjouterJeuImpl → JeuPersistenceAdapter → H2
}
